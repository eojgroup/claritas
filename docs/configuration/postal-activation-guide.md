# Postal activation guide

This is the operator runbook for provisioning Postal and enabling real personalised-briefing
delivery. Complete the stages in order. Do not enable user delivery until every readiness check in
stage 5 passes.

The implementation is safe by default:

- `POSTAL_ENABLED=false` means no Postal infrastructure exists.
- `POSTAL_ENABLED=true` and `POSTAL_EMAIL_DELIVERY_ENABLED=false` provisions Postal without running
  the Claritas email worker.
- `POSTAL_EMAIL_DELIVERY_ENABLED=true` activates scheduled delivery from the API.

## Before you start

You need:

- repository administrator access to `eojgroup/claritas`;
- permission to run GitHub Actions;
- administrative access to the authoritative DNS for `claritas.info`;
- a Google account that can verify `claritas.info` in Search Console;
- sufficient GCP permissions in project `claritas-457808` if the GitHub Terraform service account
  needs additional bootstrap roles.

Optional local tools used by the verification commands are `gh`, `gcloud`, `dig`, and `curl`.
Browser-only alternatives are included where relevant.

## 1. Configure GitHub repository variables

Open:

1. <https://github.com/eojgroup/claritas/settings/variables/actions>
2. Select **New repository variable** for each entry below.

Create these initial values:

| Name | Initial value | Notes |
| --- | --- | --- |
| `POSTAL_ENABLED` | `true` | Creates the billable Postal infrastructure. |
| `POSTAL_DOMAIN` | `briefings.claritas.info` | Keep this value unless the architecture is deliberately changed. |
| `POSTAL_ADMIN_EMAIL` | your real email address | This becomes your Postal login name. |
| `POSTAL_ENABLE_PUBLIC_PTR` | `false` | Must remain false until stage 3 is complete. |
| `POSTAL_EMAIL_DELIVERY_ENABLED` | `false` | Must remain false until stage 6. |
| `POSTAL_ENFORCE_PORT25_EGRESS` | `true` | Makes a blocked direct-delivery path fail visibly. |
| `POSTAL_SENDER_ADDRESS` | `daily@briefings.claritas.info` | Briefing From address. |
| `POSTAL_SENDER_NAME` | `Claritas` | Sender display name. |
| `POSTAL_SMTP_USERNAME` | `claritas` | Internal authenticated-submission username. |
| `POSTAL_REPLY_TO` | a monitored mailbox | Optional; omit the variable until a real support mailbox exists. |

The SMTP credential is generated by Terraform. Do not create `POSTAL_SMTP_CREDENTIAL` unless you
specifically want to override the generated value with a GitHub Actions secret.

### CLI alternative

If `gh auth status` shows that you are authenticated with repository-administration access:

```bash
repo=eojgroup/claritas
gh variable set POSTAL_ENABLED --repo "$repo" --body true
gh variable set POSTAL_DOMAIN --repo "$repo" --body briefings.claritas.info
gh variable set POSTAL_ADMIN_EMAIL --repo "$repo" --body 'YOUR_EMAIL_HERE'
gh variable set POSTAL_ENABLE_PUBLIC_PTR --repo "$repo" --body false
gh variable set POSTAL_EMAIL_DELIVERY_ENABLED --repo "$repo" --body false
gh variable set POSTAL_ENFORCE_PORT25_EGRESS --repo "$repo" --body true
gh variable set POSTAL_SENDER_ADDRESS --repo "$repo" --body daily@briefings.claritas.info
gh variable set POSTAL_SENDER_NAME --repo "$repo" --body Claritas
gh variable set POSTAL_SMTP_USERNAME --repo "$repo" --body claritas
# Optional, only when this mailbox exists and is monitored:
gh variable set POSTAL_REPLY_TO --repo "$repo" --body 'YOUR_REPLY_MAILBOX'
```

Review the values before continuing:

```bash
gh variable list --repo eojgroup/claritas
```

Do not put passwords or credentials in repository variables; GitHub variables are not masked in
workflow output. Sensitive overrides belong under **Secrets and variables → Actions → Secrets**.

## 2. Provision Postal and obtain the DNS delegation

Open the
[Terraform Infrastructure Deployment workflow](https://github.com/eojgroup/claritas/actions/workflows/terraform-deploy.yml),
select **Run workflow**, choose `main`, then select **Run workflow**.

The workflow will:

1. format, validate, and test the Terraform;
2. create the VM, static IP, persistent disk, snapshot policy, service account, Secret Manager
   secrets, firewall rules, and delegated Cloud DNS zone;
3. install and bootstrap Postal, MariaDB, and Caddy;
4. create the disabled `claritas-smtp` GKE configuration;
5. run Postal health and external-port-25 checks.

Allow roughly 10–20 minutes for the initial container pulls and bootstrap. The last port-25 check
may fail even though the infrastructure was successfully created. That is an expected hard gate and
is handled in stage 5.

Open the completed run and select **Summary**. Record:

- Postal web URL;
- static IPv4 address;
- the four `postal_dns_delegation.nameservers` values;
- the command that retrieves the generated administrator password.

If Terraform fails before creating the VM, inspect the first failing resource. The GitHub OIDC
service account is:

```text
terraform-github-oidc@claritas-457808.iam.gserviceaccount.com
```

It must be able to manage Compute Engine, Cloud DNS, Secret Manager, project/service-account IAM,
service usage, IAP access, the GKE namespace resources, and the existing Terraform state bucket.
Grant only the missing bootstrap permission and rerun the same workflow.

## 3. Delegate `briefings.claritas.info` to Cloud DNS

This operation must create a child-zone delegation. It must not replace the existing MX, SPF, or
other records at `claritas.info`.

### Try the Microsoft 365 DNS editor

1. Open <https://admin.microsoft.com>.
2. Go to **Show all → Settings → Domains**.
3. Select `claritas.info`, then **DNS records**.
4. Select **Add record**.
5. If `NS` is available, create one NS record set with:

   - **Host/name:** `briefings`
   - **Type:** `NS`
   - **TTL:** `3600` or the offered default
   - **Nameservers/values:** all four exact nameservers from the workflow summary

Some editors require four separate NS records instead of one record set. Do not include
`briefings.claritas.info` in the host field if the editor automatically appends the parent domain.
Trailing dots on nameserver values are optional in most editors.

### Stop condition: no NS record type

Microsoft-hosted DNS has historically not supported custom NS records for delegating a child zone.
If the editor does not offer `NS`, **stop here**. Do not:

- change the root nameservers immediately;
- remove the Microsoft MX record;
- replace the root SPF record;
- manually copy the Terraform-created Postal records into the parent zone.

The safe next change is to inventory the complete `claritas.info` zone and move authoritative DNS
to a provider that supports child-zone delegation, while recreating every Microsoft 365, website,
verification, and application record before switching root nameservers. That is a separate reviewed
migration; ask for that Terraform change before proceeding.

### Verify the delegation

DNS propagation can take from minutes to several hours. Run:

```bash
dig +short NS briefings.claritas.info
dig +short A postal.briefings.claritas.info
dig +short A smtp.briefings.claritas.info
dig +short MX briefings.claritas.info
dig +short TXT briefings.claritas.info
dig +short TXT postal-claritas._domainkey.briefings.claritas.info
dig +short TXT _dmarc.briefings.claritas.info
```

Expected results:

- the NS query returns the four Cloud DNS servers from the workflow;
- both A queries return the Postal static IP;
- the MX points to `smtp.briefings.claritas.info`;
- the TXT queries show SPF, DKIM, and DMARC values.

Windows PowerShell can use `Resolve-DnsName`, for example:

```powershell
Resolve-DnsName briefings.claritas.info -Type NS
Resolve-DnsName smtp.briefings.claritas.info -Type A
```

Continue only after public resolvers return the Cloud DNS records.

## 4. Verify ownership and enable reverse DNS

The target relationship must be:

```text
smtp.briefings.claritas.info  --A-->  POSTAL_STATIC_IP
POSTAL_STATIC_IP             --PTR-> smtp.briefings.claritas.info
```

### Verify ownership using the Postal A record

Google supports proving PTR-domain ownership by pointing the proposed PTR hostname at the VM's
reserved public IP. Stage 3 creates that relationship without tying the automation to a person's
Google account.

Retrieve the reserved IP and confirm the public A record matches it:

```bash
project=claritas-457808
region=europe-west2
ip=$(gcloud compute addresses describe claritas-postal-ip \
  --project "$project" --region "$region" --format='value(address)')

echo "$ip"
dig +short A smtp.briefings.claritas.info
```

Do not enable the PTR until both commands show the same IP.

### Optional: also verify the domain in Search Console

1. Sign in to [Google Search Console](https://search.google.com/search-console/) using the Google
   account that administers the domain.
2. Add a **Domain property** for `claritas.info` (preferred because it also covers the Postal
   subdomain), or `briefings.claritas.info`.
3. Choose DNS TXT verification.
4. Add the exact `google-site-verification=...` TXT value to the authoritative DNS zone requested by
   Search Console.
5. Wait until the TXT record resolves publicly, then select **Verify**.
6. Leave the verification TXT record in DNS permanently.

This is useful operational proof of control, but the matching A-record method above is the important
path for the Terraform automation. If Terraform still reports that the domain is unverified, leave
the PTR variable false and recheck that the public A record exactly matches the reserved VM IP.

### Enable and verify PTR

Change the repository variable:

```bash
gh variable set POSTAL_ENABLE_PUBLIC_PTR --repo eojgroup/claritas --body true
```

Rerun **Terraform Infrastructure Deployment**. Updating the VM access configuration can cause a
brief Postal restart.

After it completes:

```bash
project=claritas-457808
region=europe-west2
ip=$(gcloud compute addresses describe claritas-postal-ip \
  --project "$project" --region "$region" --format='value(address)')

echo "$ip"
dig +short A smtp.briefings.claritas.info
dig +short -x "$ip"
```

The forward lookup must return `$ip`, and the reverse lookup must return
`smtp.briefings.claritas.info.`.

## 5. Pass the delivery-readiness gates

### Check Postal services

The deployment workflow already runs this check. You can repeat it:

```bash
gcloud compute ssh claritas-postal \
  --project claritas-457808 \
  --zone europe-west2-b \
  --tunnel-through-iap \
  --command 'sudo /usr/local/bin/postal-healthcheck'
```

Expected output confirms that the web, public SMTP, private submission, worker, MariaDB, and Caddy
services are healthy.

Check HTTPS:

```bash
curl --fail --location --max-time 20 \
  https://postal.briefings.claritas.info/ >/dev/null && echo 'Postal HTTPS is healthy'
```

### Check direct SMTP egress

```bash
gcloud compute ssh claritas-postal \
  --project claritas-457808 \
  --zone europe-west2-b \
  --tunnel-through-iap \
  --command 'sudo /usr/local/bin/postal-port25-check'
```

Expected success:

```text
External TCP/25 egress is available ...
```

If it reports that port 25 is blocked, do not enable delivery. Google Cloud commonly blocks
external destination TCP port 25; firewall changes and Terraform cannot remove this platform
restriction. The viable choices are:

1. confirm whether this GCP project is eligible for unrestricted external port 25;
2. run the outbound MTA on infrastructure where port 25 is permitted; or
3. add an upstream SMTP relay on port 587/465.

Option 3 reintroduces an external delivery dependency and is not configured in the current Postal
Terraform. Request that code change rather than editing `/opt/postal/config/postal.yml` manually.

### Inspect Postal

Retrieve the generated password using the command from the workflow summary, or:

```bash
gcloud secrets versions access latest \
  --project claritas-457808 \
  --secret claritas-postal-admin-password
```

Sign in at <https://postal.briefings.claritas.info> using `POSTAL_ADMIN_EMAIL`. Confirm that:

- organization **Claritas** exists;
- server **Claritas Briefings** is in Live mode;
- `briefings.claritas.info` is verified;
- its SPF, DKIM, MX, and return-path checks pass;
- the message queue is empty before activation.

Treat the displayed password as sensitive. Do not paste it into tickets, chat, or workflow logs.

## 6. Enable briefing delivery and send a controlled test

Only proceed when stages 3–5 are green.

Set the final gates:

```bash
repo=eojgroup/claritas
gh variable set POSTAL_ENFORCE_PORT25_EGRESS --repo "$repo" --body true
gh variable set POSTAL_EMAIL_DELIVERY_ENABLED --repo "$repo" --body true
```

Rerun **Terraform Infrastructure Deployment**. Terraform updates the `claritas-smtp` ConfigMap and
Secret, and the workflow restarts `claritas-api` so the email worker receives the new settings.

Verify the rollout:

```bash
kubectl -n claritas rollout status deployment/claritas-api --timeout=300s
kubectl -n claritas get configmap claritas-smtp \
  -o jsonpath='{.data.PERSONAL_BRIEFING_WORKER_ENABLED}{"\n"}'
```

The second command must print `true`. Do not print the Kubernetes Secret.

Then perform one controlled application test:

1. Sign in to Claritas using an account with a real, verified email address.
2. Open **Profile → Preferences**.
3. Choose a small set of industries, companies, and regions.
4. Enable briefing email and save.
5. Select **Send preview**.
6. Confirm the message arrives and that SPF, DKIM, and DMARC pass in the received message headers.
7. Check the Postal message entry and confirm it is `Sent`, not `Held`, `Bounced`, or `Failed`.

If the preview fails, disable the worker before diagnosing:

```bash
gh variable set POSTAL_EMAIL_DELIVERY_ENABLED \
  --repo eojgroup/claritas \
  --body false
```

Rerun the Terraform workflow, then inspect:

```bash
# The disabled value is now stored in GKE. Restart the API to read it immediately;
# the current workflow only performs this restart on the enabling path.
kubectl -n claritas rollout restart deployment/claritas-api
kubectl -n claritas rollout status deployment/claritas-api --timeout=300s

kubectl -n claritas logs deployment/claritas-api -c claritas-api --since=20m

gcloud compute ssh claritas-postal \
  --project claritas-457808 \
  --zone europe-west2-b \
  --tunnel-through-iap \
  --command 'cd /opt/postal && sudo docker compose ps && sudo docker compose logs --since=20m --tail=300'
```

## Completion checklist

- [ ] GitHub variables are present and contain no secrets.
- [ ] Postal Terraform deployment is green.
- [ ] `briefings.claritas.info` is delegated to Cloud DNS.
- [ ] Postal A, MX, SPF, DKIM, return-path, and DMARC records resolve publicly.
- [ ] Forward DNS and PTR match exactly.
- [ ] External port 25 succeeds from the Postal VM.
- [ ] Postal health check and HTTPS pass.
- [ ] Postal domain checks pass in the UI.
- [ ] `POSTAL_EMAIL_DELIVERY_ENABLED=true` has been applied.
- [ ] One preview email passes SPF, DKIM, and DMARC.
- [ ] Scheduled Postal health workflow is green.
